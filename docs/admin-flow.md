# Flow หน้าแอดมินทะเบียน RPTH

อัปเดต: 26 ตุลาคม 2026

เอกสารนี้รวบรวมข้อสรุปจากการคุยกับผู้ดูแล เพื่อใช้พัฒนาหน้าแอดมินและเตรียม Google Apps Script โดยยังไม่ได้สร้างระบบบันทึกหรือ deploy Apps Script

## 1. ขอบเขตและวิธีใช้งาน

- เป็นฟอร์มกรอกข้อมูลสำหรับแอดมินและทีมงานที่ได้รับสิทธิ์ เพื่อไม่ต้องเปิดชีตแก้เอง
- การพูดคุย ตรวจหลักฐาน ตรวจเงื่อนไข และอนุมัติ ทำกันก่อนนอกระบบนี้ การกรอกเพื่อแก้ทะเบียนเป็นขั้นตอนสุดท้าย
- ไม่ต้องสร้างระบบส่งเรื่องให้ผู้นำเผ่าพันธุ์ ระบบแชต หรือคิวรออนุมัติ
- กรอกครั้งเดียว แล้วแสดงสรุปว่าจะเพิ่มหรือแก้อะไรในแต่ละชีตก่อนยืนยันบันทึก
- หน้า admin ต้องคงสูตรในชีต เติมสูตรให้แถวใหม่ที่จำเป็น และไม่เขียนทับช่วงผลลัพธ์ของสูตรแบบกระจาย
- งานบางประเภทมีหลายแถว log ต่อหนึ่งโพสต์ เลขโพสต์จึงไม่ใช่คีย์ห้ามซ้ำของทุกแถว
- ไม่แก้ไข log ย้อนหลังเพื่อให้ตาม Slot ปัจจุบัน

## 2. ชีตที่เกี่ยวข้อง

| ชีต | หน้าที่ |
| --- | --- |
| Users | UserID, Username, ประเภทผู้ใช้ และสถานะที่สูตรดึงมา |
| Characters | ตัวละคร, CharID, Slot, เฟซเคลม, ลิงก์ประวัติ, Is Active Character |
| Player | ชื่อหลัก เผ่าพันธุ์ สลอตที่ใช้งาน ช่องตรวจสถานะ สูตรวันใช้งานและค่าธรรมเนียม |
| Staff | ข้อมูลทีมงานและ Role; ยังไม่ได้กำหนดฟอร์มเพิ่ม/แก้ Staff |
| NPC | ข้อมูล NPC โดยตรง |
| log ลงทะเบียนตัวละคร | ประวัติจากกระทู้จุดลงทะเบียนตัวละคร |
| log Admin | เหตุการณ์ที่แอดมินปรับสถานะ/อนุมัติและใช้คำนวณย้อนหลัง |
| log เฟซเคลมล็อก | เหตุการณ์เริ่มล็อก ต่ออายุ พักนับ นับต่อ และยกเลิก |
| Faceclaim Locks | สรุปสิทธิ์ล็อกและวันที่จาก log โดยสูตร |
| Public Player / Public Character / Public Staff / Public NPC / Public Faceclaim Locks | ข้อมูลที่เผยแพร่ให้ dashboard และสคริปต์อ่าน |

### คอลัมน์หลักของ log ลงทะเบียนตัวละคร

`logID (#Post)`, `UserID`, `Type`, `Old Name`, `New Name`, `Old Face Claim`, `New Face Claim`, `From Slot`, `To Slot`, `Effective Date`, `Affects Usage`, `User Status`, `Note`

### คอลัมน์หลักของ log Admin

`LogID`, `UserID`, `Type`, `Character Name`, `Face Claim`, `From Slot`, `To Slot`, `Effective Date`, `Affects Usage`, `User Status`, `Count As Main Change`, `Count As Reclaim`, `Note`

### คอลัมน์ข้อมูลนำเข้าของ log เฟซเคลมล็อก

`EventID`, `LockID`, `logID (#Post)`, `CharID`, `UserID`, `Lock Character Name`, `Lock Face Claim`, `Type`, `Effective Date`, `Lock Time (Month)`, `Note`

คอลัมน์คำนวณถัดจากนี้ให้คงการทำงานของสูตรเดิม ตรวจชื่อและขอบเขตสูตรจริงในชีตปัจจุบันก่อนเชื่อม Apps Script

## 3. ตัวตนของตัวละคร สลอต และการเก็บตัวที่เลิกใช้

- หนึ่งบัญชีมี MAIN 1 ตัว และตัวรองปกติไม่เกิน 2 ตัว ยกเว้นมีสิทธิ์เพิ่มตัวรอง
- CharID ผูกกับตัวละคร ไม่ผูกกับตำแหน่ง MAIN/SUB หลังจากใช้ระบบใหม่
- เปลี่ยนชื่อ เปลี่ยนเฟซเคลม หรือย้าย Slot ของตัวละครเดิม: คง CharID
- สร้างตัวละครใหม่ รวมถึงสร้างตัวหลักใหม่: สร้าง CharID ใหม่ ไม่ใช้ CharID เก่าซ้ำ
- ข้อสรุปล่าสุดนี้แทนแนวคิดเดิมที่เคยจะใช้ CharID ของ MAIN เก่ากับตัวหลักใหม่
- รูปแบบ CharID เดิม เช่น `C-758-01`; วิธีจัดสรรเลขต้องไม่ซ้ำกับตัวที่เก็บเป็นประวัติแล้ว
- ตัวที่นำออกจากทะเบียนปัจจุบันให้เก็บแถวเดิมไว้ เปลี่ยน Slot เป็น `-` และเอา Is Active Character ออก
- Slot `-` ไม่นับโควตาตัวรอง ไม่ให้เลือกสลับใช้งาน และไม่แสดงใน dashboard ปัจจุบัน
- โค้ด dashboard ที่มีอยู่ยังต้องเพิ่มการกรอง Slot `-` ก่อนนำวิธีนี้มาใช้จริง
- ผู้ดูแลไม่คาดว่าจะมีกรณีนำตัวละครที่ยังล็อกเฟซเคลมออกจากทะเบียน อย่ากำหนดพฤติกรรมยกเลิกสิทธิ์นี้เอง

### ความหมายของ From/To Slot

- เหตุการณ์สลับใช้งานใช้ From/To บอกตัวที่ใช้งานก่อนและหลัง เพื่อคำนวณวันใช้งาน ไม่ใช่ประวัติการย้ายสลอตของตัวละครทุกตัว
- เหตุการณ์เปลี่ยนชื่อ/เฟซเคลมระบุตัวละครด้วย UID และ From/To ที่เป็นสลอตเดียวกัน เช่น `MAIN → MAIN`, `SUB 1 → SUB 1`
- แถวย้าย MAIN เดิมไปเป็นตัวรองเป็นเหตุการณ์โครงสร้างเพิ่มเติม และไม่ติ๊ก Affects Usage
- log เก็บสลอต ณ วันเกิดเหตุการณ์ ไม่ต้องเปลี่ยนตาม Characters ภายหลัง

## 4. กระทู้จุดลงทะเบียนตัวละคร

### 4.1 ลงทะเบียนผู้เล่นใหม่

เริ่มบันทึกหลังผู้นำเผ่าพันธุ์ตรวจผ่านและแอดมินจัดการเรียบร้อยแล้ว

ข้อมูล: UID, เลขโพสต์, วันที่ลงฟอร์ม, ชื่อตัวละคร, เฟซเคลม, ลิงก์ประวัติ, เผ่าพันธุ์ และประเภท Player

| ชีต | สิ่งที่บันทึก |
| --- | --- |
| Users | UID, Username ตามชื่อตัวละคร, ประเภท Player และสูตรสถานะ |
| Characters | UID, CharID ใหม่, ชื่อ, เฟซเคลม, MAIN, ลิงก์ประวัติ และ Active = TRUE |
| Player | UID, ชื่อหลัก, Race, Active Character = MAIN, สูตรที่จำเป็น, Post Check = TRUE, Activity Check = TRUE, Exempt Note = `สมัคร dd/MM/yyyy` |
| log ลงทะเบียนตัวละคร | Type = `ลงทะเบียนตัวละครใหม่`, New Name/Face Claim, `NEW → MAIN`, วันที่ลงฟอร์ม, Affects Usage = FALSE |

- วันที่ `สมัคร` ใน Note ใช้วันที่ลงฟอร์มเดียวกับ log
- ตรวจ UID ซ้ำก่อนเพิ่มผู้เล่น; หากพบผู้ใช้เดิมต้องไม่เพิ่มซ้ำโดยอัตโนมัติ

### 4.2 เปลี่ยนชื่อ/เฟซเคลมตัวละครปัจจุบัน

- รับเลขโพสต์ UID วันที่ลงฟอร์ม และสลอตของตัวละครที่จะเปลี่ยน
- แสดงชื่อและเฟซเคลมเดิมให้ตรวจ แล้วกรอกชื่อใหม่/เฟซเคลมใหม่ตามกรณี
- ช่องใหม่ที่ว่างหมายถึงคงค่าเดิม
- ไม่ใช้ลิงก์ประวัติจากฟอร์มนี้
- From/To เป็นสลอตเดียวกัน, Affects Usage = FALSE, คง CharID
- Type ตามการเปลี่ยนจริง: `เปลี่ยนชื่อ`, `เปลี่ยนเมจ`, `เปลี่ยนชื่อ+เมจ`

| สิ่งที่เปลี่ยน | ชีตที่แก้ |
| --- | --- |
| ชื่อ MAIN | Users, Characters, Player |
| ชื่อตัวรอง | Characters |
| เฟซเคลม MAIN หรือตัวรอง | Characters |

เพิ่ม log ลงทะเบียนตัวละครทุกกรณี เก็บค่าเก่าก่อนแก้

### 4.3 ลงทะเบียนตัวละครรองใหม่

- ใช้ฟอร์มนี้ครั้งแรกที่สร้างตัวรองตัวนั้น และต้องสลับไปใช้ตัวที่เพิ่มทันที
- ต้นทางอาจเป็น MAIN หรือตัวรองที่กำลังใช้อยู่ เช่น `MAIN → SUB 1` หรือ `SUB 1 → SUB 2`
- เพิ่มแถว Characters พร้อม CharID ใหม่ สลอตรองที่ว่าง ชื่อ เฟซเคลม ลิงก์ประวัติตัวรอง และ Active = TRUE
- เอา Active ของตัวต้นทางออก; ล้างเฟซเคลมต้นทางเฉพาะเมื่อไม่มีสิทธิ์ล็อกเฟซเคลมนั้น
- Player เปลี่ยน Active Character เป็นสลอตตัวใหม่
- log: Type = `ลงทะเบียนตัวละครรอง`, ชื่อ/เฟซเคลมตัวที่ใช้อยู่เดิมและตัวใหม่, From/To ตามจริง, วันที่ลงฟอร์ม, Affects Usage = TRUE
- เก็บชื่อและเฟซเคลมต้นทางลง log ก่อนล้าง
- ตรวจโควตา 2 ตัวรอง หรือสิทธิ์เพิ่มตัวรองของบัญชี

### 4.4 สลับใช้งานตัวละครหลัก–รองที่มีอยู่แล้ว

- ไม่สร้างแถวตัวละครหรือ CharID ใหม่
- ไม่ใช้ลิงก์ประวัติจากฟอร์มนี้
- log: Type = `สลับตัวหลัก-รอง`, ชื่อ/เฟซเคลมตัวปัจจุบันและปลายทาง, From/To ตามจริง, วันที่ลงฟอร์ม, Affects Usage = TRUE
- Characters: เอา Active ของต้นทางออก ติ๊กให้ปลายทาง และใส่เฟซเคลมที่แจ้งให้ปลายทาง
- ล้างเฟซเคลมของตัวที่เลิกใช้เฉพาะเมื่อไม่มีสิทธิ์ล็อกที่ตรงกับเฟซเคลมนั้น
- Player: Active Character เป็นสลอตปลายทาง
- เตรียมเหตุการณ์ล็อกพักนับ/นับต่อและแสดงในหน้าสรุปเดียวกัน ตามหัวข้อ 6

### 4.5 เปลี่ยนตัวละครหลัก

กฎ: MAIN มีหนึ่งตัว ต้องใช้งานไม่ต่ำกว่า 6 เดือนในช่วง 1 มกราคม–20 ธันวาคมของทุกปี

ค่าธรรมเนียมเปลี่ยนตัวหลัก: ฟรีครั้งแรก ครั้งถัดไป 5,000 ยกเว้นโควตาพิเศษ หน้า Player คำนวณจำนวนและค่าธรรมเนียมจาก log อยู่แล้ว หน้าแอดมินยังไม่ต้องทำระบบรับเงินหรือหักโควตาฟรี

| กรณี | การบันทึก log เปลี่ยนตัวหลัก |
| --- | --- |
| ใช้ MAIN อยู่และนำตัวรองเดิมขึ้น MAIN | ทำรายการสลับไปใช้ตัวรองนั้นก่อน แล้วจึงเลื่อนเป็น MAIN |
| ใช้ตัวรองอยู่และนำตัวนั้นขึ้น MAIN | สลอตตัวรองนั้น → MAIN, Affects Usage = TRUE; ระบบเติมชื่อ/เมจจากตัวที่เลือกได้ ไม่ต้องให้แอดมินพิมพ์ใหม่ |
| ใช้ MAIN อยู่และสร้าง MAIN ใหม่ | NEW → MAIN, Affects Usage = FALSE |
| ใช้ตัวรองอยู่และสร้าง MAIN ใหม่ | สลอตที่ใช้อยู่ → MAIN, Affects Usage = TRUE ตามตัวอย่างโพสต์ 1104 ของ UID 503 |

- Type แถวหลัก = `เปลี่ยนตัวละครหลัก`
- วันที่มีผลเป็นวันที่ลงฟอร์ม
- สร้างตัวใหม่ให้สร้าง CharID ใหม่เสมอ; ตัวเดิมที่เลื่อนเป็น MAIN คง CharID และเปลี่ยน Slot
- หากเลือกตัวรองที่ไม่ได้กำลังใช้อยู่ ให้สลับใช้งานก่อน ไม่รวมเป็นการเลือกตัวอื่นขึ้น MAIN โดยข้ามขั้นตอน
- Player เปลี่ยน Display Name เป็นชื่อหลักใหม่ และ Active Character = MAIN
- Users เปลี่ยน Username เป็นชื่อหลักใหม่
- Characters ปรับ Slot และ Active ให้ตรงกับผลสุดท้าย; สิทธิ์ล็อกต้องตรวจด้วย CharID ไม่ใช่ชื่อหรือสลอต
- การจัดการลิงก์ประวัติกรณีเปลี่ยน MAIN ยังต้องยืนยันก่อนพัฒนา ห้ามสลับลิงก์ของคนละตัวโดยอิงเลขท้าย CharID

หากเก็บตัวหลักเดิมเป็นตัวรอง เพิ่ม log อีกแถว:

- เลขโพสต์และ UID เดียวกับแถวเปลี่ยนตัวหลัก
- Type = `ย้ายตัวละครหลักเดิมเป็นตัวรอง`
- Old Name / New Name = ชื่อตัวหลักเดิมทั้งสองช่อง
- ช่องเฟซเคลมว่าง
- MAIN → สลอตรองที่จะเก็บ, วันที่เดียวกัน, Affects Usage = FALSE
- คง CharID ของตัวหลักเดิมและเปลี่ยน Slot
- หากเลื่อนตัวรองขึ้น MAIN สามารถใช้สลอตรองที่เพิ่งว่างรับตัวหลักเดิม
- หากโควตารองเต็มและสร้าง MAIN ใหม่ ให้แอดมินเลือกตัวรองที่จะถูกแทนที่ หรือระบุว่ามีสิทธิ์เพิ่มตัวรอง
- ตัวที่ถูกแทนที่/ไม่เลือกเก็บให้ Slot = `-` และ Active = FALSE โดยคงประวัติและ CharID
- หน้าสรุปต้องระบุให้ชัดว่าตัวใดจะออกจากทะเบียนปัจจุบัน

ตัวอย่างอ้างอิง:

- UID 600 โพสต์ 1024: Franklin จาก SUB 2 เป็น MAIN; Quineth จาก MAIN เป็น SUB 2; Arthur คง SUB 1
- UID 637 โพสต์ 998: Lopez จาก SUB 1 เป็น MAIN; Dylan จาก MAIN เป็น SUB 1
- ตัวอย่างเก่าบางส่วนสร้าง CharID หลังเกิดเหตุการณ์ จึงไม่ใช้เลข CharID ในตัวอย่างเป็นกฎว่าต้องผูกกับ Slot
- UID 600 โพสต์ 956 (`NEW → MAIN` ขณะใช้ MAIN) เคยติ๊ก TRUE ผิด ผู้ดูแลแก้เป็น FALSE แล้ว

### 4.6 เปลี่ยนเผ่าพันธุ์

- Player: แก้ Race เป็นเผ่าพันธุ์ใหม่
- log ลงทะเบียนตัวละคร: Type = `เปลี่ยนเผ่าพันธุ์`, Old Name/Old Face Claim ของตัวที่เกี่ยวข้อง, New Name/New Face Claim ว่าง
- From/To เป็นสลอตเดียวกัน ตามตัวอย่าง MAIN → MAIN
- วันที่ลงฟอร์ม, Affects Usage = FALSE
- Note = `เผ่าพันธุ์เก่า > เผ่าพันธุ์ใหม่`
- ไม่เปลี่ยนชื่อ CharID เฟซเคลม หรือ Active และไม่ใช้ลิงก์ประวัติ

### 4.7 ลงทะเบียนหลังถูกถอนเฟซเคลม / ยื่นเฟซเคลมหลุด

รับวันที่ลงฟอร์มและวันที่อนุมัติแยกกัน ไม่ใช้ลิงก์ประวัติจากฟอร์ม

**ไม่ผ่าน**

- เพิ่มเฉพาะ log ลงทะเบียนตัวละคร: Type = `เฟซเคลมหลุด (ไม่สำเร็จ)`, User Status = Inactive
- ชื่อ/เฟซเคลมเก่าและค่าที่ขอใหม่ถ้ามี, From/To สลอตเดียวกัน, Affects Usage = FALSE, วันที่ลงฟอร์ม
- ไม่เปลี่ยนข้อมูลทะเบียนหรือสถานะเดิม

**ผ่าน**

- Characters: ใส่เฟซเคลมกลับ; ถ้ามีชื่อ/เมจใหม่ให้ใช้ค่าใหม่ ไม่มีก็ใช้ค่าเดิม และติ๊ก Active Character
- ถ้าเปลี่ยนชื่อ MAIN แก้ Users และ Player ตามด้วย
- Player: ติ๊ก Reclaim Approved
- log ลงทะเบียนตัวละคร: Type = `เฟซเคลมหลุด`, User Status = Active, Affects Usage = FALSE, วันที่ลงฟอร์ม
- log Admin: Type = `ยืนยันเฟซเคลมหลุดผ่าน`, ชื่อ/เฟซเคลมหลังอนุมัติ, From/To สลอตเดียวกัน, **วันที่อนุมัติผ่าน**, Affects Usage = TRUE, User Status = Active, Count As Main Change = FALSE, Count As Reclaim = TRUE
- Note ใน log Admin อ้างอิงโพสต์ที่ยื่น เช่น `#1108` พร้อมลิงก์โพสต์
- ไม่เพิ่มเหตุการณ์ปรับ Inactive ซ้ำในขั้นอนุมัติ; ตัวอย่างแถว `ปรับ inactive` เป็นเหตุการณ์ก่อนหน้าอีกวันหนึ่ง

## 5. เพิ่ม NPC ใหม่

- ทีมงานแจ้งชื่อ เฟซเคลม และเผ่าพันธุ์ จากนั้นแอดมินตรวจว่ามีแอ็กเคานต์ NPC หรือไม่
- เพิ่มเฉพาะชีต NPC ไม่เพิ่ม Users, Characters, Player หรือ log
- ฟอร์ม: `UserID`, `Display Name`, `Faceclaim`, `Race`, `Link` (ไม่มีให้ว่าง)
- มีแอ็กเคานต์ใช้ UID จริง; ไม่มีให้ระบบเลือกรหัสตัวอักษรถัดไปที่ยังไม่ซ้ำ เช่น a, b, c
- การต่อรหัสหลัง z ยังไม่ได้ระบุ ต้องกำหนดก่อนใช้งานจริง

## 6. กระทู้ระบบล็อกเฟซเคลม

### 6.1 กฎสิทธิ์

- สมาชิกล็อกพร้อมกันสูงสุด 2 สิทธิ์ รวมสิทธิ์ที่พักนับ
- เหมาจ่าย 30,000 ได้ 12 เดือน; รายเดือน 3,000 ต่อเดือนตามจำนวนเดือนที่ต้องการ
- เริ่มคุ้มครองจากวันที่อนุมัติ
- ห้ามล็อกเฟซเคลมที่ผู้อื่นกำลังใช้หรือมีสิทธิ์ล็อกอยู่
- สิทธิ์ผูกกับ UserID + CharID + เฟซเคลม ไม่ย้ายตาม Slot หรือชื่อ
- ล็อกเฟซเคลมเดียวกันให้ตัวละครอื่นของตนต้องจ่ายเพิ่มและนับโควตาอีกสิทธิ์
- ไม่เพิ่มหรือโอนสิทธิ์ให้สมาชิกอื่น
- ยกเลิกก่อนหมดอายุได้ แต่ไม่คืนเงิน
- ระหว่างรออนุมัติกันสิทธิ์ในกระทู้; หน้า admin บันทึกหลังจัดการทุกอย่างแล้ว ไม่มีคิวรออนุมัติ
- ไม่ใช้ภาพเฟซเคลมแนบในระบบทะเบียน
- แอดมินตรวจหลักฐานชำระเงินแล้วระบุแผน/จำนวนเดือน หน้า admin ไม่ใช่ระบบรับชำระเงิน

### 6.2 เหตุการณ์ที่บันทึก

| เหตุการณ์ | วิธีบันทึก |
| --- | --- |
| เริ่มล็อก | EventID ใหม่, LockID ใหม่, Type = เริ่มล็อก, วันที่อนุมัติ, จำนวนเดือน |
| ต่ออายุขณะยังไม่หมดกำหนด | EventID ใหม่, LockID เดิม, Type = ต่ออายุ |
| กลับมาใช้ตัวละครและเฟซเคลมที่ล็อก | เพิ่มเหตุการณ์พักนับ |
| สลับไปใช้ตัวละครอื่น | เพิ่มเหตุการณ์กลับมานับต่อของสิทธิ์ที่พักอยู่ |
| ตัวเดิมที่พักนับแต่เปลี่ยนไปใช้เมจอื่น | เป็นกรณีพิเศษ อาจยกเลิกล็อก ต้องจัดการ/ตกลงก่อน ไม่ตัดสินเอง |

- ชื่อ Type ของเหตุการณ์กลับมานับต่อ/ยกเลิกต้องตรวจค่าที่สูตรชีตรองรับก่อนลงมือ ไม่ตั้งชื่อใหม่โดยเดา
- กรณีต่ออายุหลังหมดอายุเดิม รวมถึงวิธีใช้ LockID และวันเริ่มรอบใหม่ ยังต้องยืนยันกับผู้ดูแลและสูตรเดิม
- Faceclaim Locks และ Public Faceclaim Locks ใช้สูตรคำนวณจากเหตุการณ์ ไม่ให้หน้า admin เขียนทับผลสรุป

### 6.3 เชื่อมกับการเปลี่ยนตัวละคร

ระบบเตรียมเหตุการณ์อัตโนมัติและแสดงรวมในหน้าสรุป ไม่ให้แอดมินกรอกซ้ำ

| สิ่งที่พบ | ผลที่เตรียมบันทึก |
| --- | --- |
| ตัวต้นทางที่เลิกใช้มีสิทธิ์ล็อกตรงกับเฟซเคลม | เก็บเฟซเคลมไว้ ไม่ล้าง |
| สิทธิ์ของต้นทางกำลังพักนับ | กลับมานับต่อ |
| ต้นทางไม่มีสิทธิ์ล็อกเฟซเคลมนั้น | ล้างเฟซเคลมตาม flow สลับตัวละคร |
| ปลายทางใช้เฟซเคลมที่สิทธิ์กำลังนับอยู่ | พักนับ |
| สิทธิ์อยู่ในสถานะที่ต้องการอยู่แล้ว | ไม่สร้างเหตุการณ์ซ้ำ |
| สิทธิ์กับเฟซเคลมไม่ตรงกัน/เป็นกรณีพิเศษ | แจ้งให้แอดมินตรวจและจัดการก่อนบันทึก |

- เหตุการณ์พักนับ/นับต่อจากการสลับ ใช้ **วันที่ลงฟอร์มสลับ** เดียวกับ log ลงทะเบียน
- ไม่ตีความว่าทุกการเปลี่ยน Slot ต้องพักหรือนับต่อ ถ้าตัวที่ใช้งานและเฟซเคลมไม่เปลี่ยน ให้ตรวจสถานะจริงก่อน
- การปรับ Inactive ที่มีสิทธิ์ล็อกเกี่ยวข้องยังไม่ได้ตกลงว่าจะจัดการอย่างไร ต้องยืนยันก่อนเชื่อมอัตโนมัติ

## 7. ตรวจ Active และช่วงยกเว้นตรวจ

### 7.1 กฎและขั้นตอนตรวจ

- ตรวจช่วงต้นเดือน ย้อนหลัง 3 เดือน
- เกณฑ์โพสต์: อย่างน้อย 20 โพสต์ (20 ผ่าน ไม่ใช่ต้อง 21)
- เกณฑ์กิจกรรม: อย่างน้อย 1 กิจกรรมเล็ก/กลาง/ใหญ่ หรือเทศกาล ภายใน 3 เดือน
- ผู้ดูแลใช้สคริปต์ตรวจโพสต์ แล้วส่งรายชื่อที่จำเป็น/ไม่มั่นใจให้ทีมงานช่วยตรวจกิจกรรม
- Post Check, Activity Check และ Reclaim Approved ยังคงจัดการแบบ manual หลังตรวจเสร็จ
- Exempt Until ใช้คัดกรองรอบตรวจ ไม่ทำให้สถานะทะเบียนหายหรือเปลี่ยนเป็น Inactive อัตโนมัติเมื่อถึงวัน

### 7.2 แหล่งวันที่ยกเว้นตรวจ

- สมัครใหม่: วันลงทะเบียนตัวละครใหม่จาก log + 3 เดือนปฏิทิน
- Reclaim ผ่าน: วันอนุมัติจริงจาก log Admin + 3 เดือนปฏิทิน ไม่ใช้วันยื่นฟอร์ม
- Player เก็บ Reclaim Approved At และ Exempt Until; Exempt Until เลือกวันสิ้นสุดที่มาทีหลังจากสองสิทธิ์
- ไม่อ่าน Exempt Note เพื่อคำนวณในสคริปต์อีก เพราะมีคอลัมน์วันที่ที่คำนวณตรงจาก log แล้ว
- Note บางรายการเคยคลาดเคลื่อนจากวันอนุมัติ ให้ยึด log Admin ที่ถูกต้องเป็นข้อมูลหลัก
- Public Player ส่ง Exempt Until เพิ่มต่อท้ายข้อมูล A:H แล้ว
- ปัจจุบันสคริปต์ยกเว้นรวมวัน Exempt Until และเปรียบเทียบวันปัจจุบันตาม Asia/Bangkok

### 7.3 สคริปต์ตรวจโพสต์ที่มีอยู่

ไฟล์ในโปรเจกต์: `activity-check.js`

- รันบน roleplayth.com ขณะล็อกอิน ไม่ได้ฝังในหน้าแอดมินในขณะนี้
- ดึงรายชื่อผู้เล่น Active จาก Public Player ไม่ต้องกรอก UID ทีละคน
- ยกเว้นตรวจตาม Exempt Until ก่อนร้องขอหน้าค้นหาโพสต์
- หยุดนับเมื่อถึง 20 และรายงาน 20+ ไม่ได้อ้างว่าเป็นจำนวนโพสต์ทั้งหมด
- แยก EXEMPT, ไม่ผ่าน, ตรวจไม่สำเร็จ และยังไม่ได้ตรวจ; ข้อผิดพลาดไม่ใช่การไม่ผ่าน
- ไม่แก้ข้อมูลหรือสถานะในชีต
- คัดลอกผู้ไม่ผ่าน: `copy(window.RP_ACTIVITY_FAILED_TSV)`
- คัดลอกผู้ยกเว้น: `copy(window.RP_ACTIVITY_EXEMPT_TSV)`
- คัดลอกผลทั้งหมด: `copy(window.RP_ACTIVITY_TSV)`
- หยุด: `window.STOP_ACTIVITY = true`
- ผลที่รัน 26 ตุลาคมเป็นผลตรวจเบื้องต้น ผู้ดูแลจะตรวจใหม่ต้นเดือนพฤศจิกายน ไม่ถือเป็นคำสั่งปรับสถานะ

### 7.4 หน้า “ปรับ Inactive แบบหลายคน” — ข้อสรุปล่าสุด

หน้านี้มีไว้ **ลงมือปรับจากรายชื่อที่ตรวจและตกลงแล้ว** ไม่ใช่หน้าทบทวนผลโพสต์/กิจกรรมซ้ำ

1. วางรายชื่อทั้งหมดครั้งเดียว หนึ่งคนต่อบรรทัด รองรับชื่อหรือ UID
2. เลือกวันที่ปรับ Inactive
3. ตรวจสอบและสรุป: จับคู่ UID แสดงชื่อ ตัวที่ใช้อยู่ สลอต และเฟซเคลมที่จะล้าง
4. แยกรายชื่อซ้ำ หาไม่พบ ชื่อกำกวม และผู้ที่เป็น Inactive อยู่แล้ว ไม่เดาจับคู่หรือสร้าง log ซ้ำ
5. แอดมินตรวจสรุปและยืนยันปรับทั้งหมด

เมื่อยืนยัน:

- Player: ปรับช่องตรวจที่เกี่ยวข้องให้สถานะเป็น Inactive โดยไม่ต้องให้แอดมินกรอกผลตรวจโพสต์/กิจกรรมซ้ำในฟอร์มนี้
- Characters: ล้างเฟซเคลมและเอา Is Active Character ของตัวที่ใช้อยู่ก่อนปรับออก
- log Admin: Type = `ปรับ inactive`, ชื่อ/เฟซเคลมก่อนล้าง, From/To สลอตที่ใช้อยู่เหมือนกัน, วันที่ปรับ Inactive ที่เลือก, Affects Usage = TRUE, User Status = Inactive, Count As Main Change = FALSE, Count As Reclaim = FALSE
- ไม่เพิ่ม log ลงทะเบียนตัวละคร เพราะไม่เกี่ยวกับฟอร์มในกระทู้
- รายละเอียดว่าจะตั้ง Post Check / Activity Check / Reclaim Approved เป็นค่าใดในแต่ละช่องยังต้องกำหนดก่อนเขียนส่วนบันทึก โดยต้องไม่เหลือ Reclaim Approved ที่ทำให้สูตรยัง Active และไม่สร้างผลตรวจที่ไม่เคยตรวจจริง
- ไม่เปลี่ยนชื่อหรือ Slot ปัจจุบันใน Player เป็น `-` เพียงเพราะบัญชี Inactive; `-` ใช้กับตัวละครที่นำออกจากทะเบียนตามหัวข้อ 3

## 9. เตรียมเชื่อม Google Apps Script

ส่วนนี้เป็นรายการงานที่ต้องทำก่อนใช้งานจริง ไม่ใช่การยืนยันว่าได้ติดตั้งหรือกำหนดสถาปัตยกรรมแล้ว

### สิ่งที่ต้องเตรียม/ตัดสินใจ

- Spreadsheet ID ของชีตหลักและบัญชีที่ใช้ deploy
- วิธีล็อกอิน รายชื่อแอดมินที่อนุญาต และขอบเขตสิทธิ์ของแต่ละคน
- วิธีให้หน้าแอดมินเรียก Apps Script และรูปแบบ deployment; หน้าเว็บปัจจุบันอ่าน CSV ได้อย่างเดียว
- ตรวจหัวคอลัมน์ สูตรปัจจุบัน ช่องติ๊ก และช่วงสูตรกระจายจากไฟล์/ชีตล่าสุดอีกครั้ง
- ยืนยันรายการที่ระบุว่ายังค้างในเอกสารนี้ โดยเฉพาะเหตุการณ์ล็อกและค่าช่องตรวจเมื่อปรับ Inactive
- ยังไม่มีระบบจัดการโควตาพิเศษถาวร ต้องตกลงว่าจะเก็บสิทธิ์เพิ่มตัวรองไว้ที่ใด

### ข้อเสนอด้านการบันทึกเพื่อให้หลายคนใช้งานได้

- ตรวจสิทธิ์ที่ฝั่ง Apps Script ทุกคำสั่งเขียน ไม่อาศัยการซ่อนปุ่มหน้าเว็บ
- แยกขั้นเตรียมสรุปกับยืนยันบันทึก และตรวจข้อมูลล่าสุดอีกครั้งก่อนเขียน
- ตรวจ UID/CharID/LockID ความซ้ำ สลอตและโควตาที่ฝั่งรับคำสั่งด้วย
- ใช้รหัสคำขอบันทึกเพื่อป้องกันการกดซ้ำ/ส่งซ้ำ โดยไม่ใช้เลขโพสต์เพียงอย่างเดียว
- จัดสรร ID และเขียนข้อมูลหลายชีตภายใต้กลไกป้องกันงานชนกัน
- กำหนดการตรวจผล/กู้คืนเมื่อเขียนได้เพียงบางชีต เพราะ Google Sheets ไม่ใช่ฐานข้อมูลที่มี transaction หลายชีตอัตโนมัติ
- เก็บผู้ดำเนินการ เวลา และผลการบันทึกเพื่อสอบกลับ โดยไม่เปลี่ยนความหมาย Effective Date ของแต่ละ flow
- ห้ามใส่ข้อมูลลับหรือสิทธิ์เขียนชีตไว้ใน JavaScript สาธารณะของ dashboard

### ลำดับพัฒนาที่เสนอ

1. ยืนยันสูตร/หัวคอลัมน์และรายละเอียดที่ค้าง แล้วเตรียม Apps Script กับสิทธิ์แอดมิน
2. ทำฟอร์มลงทะเบียนผู้เล่นใหม่ให้บันทึกครบ Users / Characters / Player / log พร้อมหน้าสรุป
3. เพิ่มแก้ชื่อ/เมจ เพิ่ม NPC เปลี่ยนเผ่าพันธุ์
4. เพิ่มตัวรอง สลับใช้งาน เปลี่ยน MAIN และเชื่อมเหตุการณ์ล็อก
5. เพิ่มฟอร์มล็อก/ต่ออายุและยื่นเฟซเคลมหลุดผ่าน
6. เพิ่มปรับ Inactive แบบวางรายชื่อหลายคน

ลำดับนี้ปรับได้ตามผู้ดูแล เอกสารเป็นข้อมูลสำหรับเริ่มพัฒนา ไม่ได้อนุญาตให้ deploy หรือเขียนข้อมูลจริงโดยไม่อยู่ในคำสั่งงานนั้น
